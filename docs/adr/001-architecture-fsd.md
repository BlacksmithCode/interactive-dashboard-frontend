# 001. Выбор архитектуры Feature-Sliced Design (FSD)

## Статус
Accepted

## Контекст
При начале разработки проекта Interactive Dashboard Frontend стояла задача выбрать архитектурный подход, который обеспечит:

- Четкое разделение ответственности между модулями
- Масштабируемость для growing HR-системы
- Удобство онбординга новых разработчиков
- Переиспользуемость кода
- Тестируемость отдельных частей системы

Традиционные подходы (MVC, MVP, MVVM) не полностью отвечали требованиям фронтенд-разработки, а популярные альтернативы имели свои недостатки.

## Решение
Было решено использовать методологию Feature-Sliced Design (FSD) - современную архитектуру для фронтенд-приложений, которая организует код в слои:

```
src/
├── app/           # App слой (инициализация, роутинг, глобальные стили)
├── pages/         # Pages слой (страницы приложения)
├── widgets/       # Widgets слой (композиции UI)
├── features/      # Features слой (бизнес-фичи)
├── entities/      # Entities слой (бизнес-сущности)
└── shared/        # Shared слой (переиспользуемый код)
```

Каждый слой имеет четкую зону ответственности и правила взаимодействия с другими слоями.

## Последствия

### Преимущества

1. **Четкое разделение ответственности**: Каждый слой имеет свою зону ответственности
2. **Масштабируемость**: Новые фичи добавляются без влияния на существующий код
3. **Переиспользуемость**: Entities и shared код могут использоваться в разных фичах
4. **Тестируемость**: Каждый слой можно тестировать независимо
5. **Быстрый онбординг**: Новые разработчики быстро понимают структуру проекта
6. **Единые правила**: Стандартизированный подход к организации кода

### Недостатки

1. **Больше файлов**: Требуется создавать больше файлов и папок
2. **Изначальная сложность**: Новая команда должна изучить FSD концепции
3. **Больше "boilerplate"**: Требуется больше шаблонного кода для новых фич

### Влияние на систему

- Все новые фичи следуют FSD структуре
- Компоненты организованы по бизнес-фичам, а не по типу
- API-слой отделен от UI-слоя
- Состояние управляется на уровне фичей

## Альтернативы

### Альтернатива 1: Classic MVC
- **Описание**: Традиционная модель-вид-контроллер архитектура
- **Почему не выбрана**: Не подходит для современных React-приложений, смешивает ответственность

### Альтернатива 2: Atomic Design
- **Описание**: Организация компонентов по атомам, молекулам, организмам
- **Почему не выбрана**: Фокусируется только на UI-компонентах, не учитывает бизнес-логику

### Альтернатива 3: Redux + Ducks
- **Описание**: Redux с паттерном ducks для организации кода
- **Почему не выбрана**: Избыточная сложность для нашего случая, много бойлерплейта

### Альтернатива 4: Feature-based (без слоев)
- **Описание**: Организация по фичам без четкого разделения на слои
- **Почему не выбрана**: Может привести к смешиванию ответственности и дублированию кода

## Реализация

В проекте FSD реализован через:

1. **Структуру папок** - строгая иерархия слоев
2. **Правила импорта** - нижние слои не зависят от верхних
3. **Именованные экспорты** - для лучшей tree-shaking оптимизации
4. **Типизацию** - строгая TypeScript типизация на всех уровнях
5. **Документацию** - каждый слой имеет свою документацию

## Пример структуры фичи

```
src/features/dashboard/
├── api/           # API вызовы
├── model/         # Состояние и бизнес-логика
├── ui/            # UI компоненты
├── hooks/         # React хуки
├── config/        # Конфигурация
└── index.ts       # Публичные экспорты
```
