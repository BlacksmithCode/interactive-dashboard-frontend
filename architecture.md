# Архитектура проекта Interactive Dashboard Frontend

## 1. Предыдущая архитектура (До перехода на FSD)

До начала рефакторинга и внедрения Feature-Sliced Design (FSD), проект имел традиционную «плоскую» структуру, организованную по типам файлов (Layer-first подход). Это стандартный шаблон для многих React-приложений на начальных этапах разработки.

### Как выглядела старая структура:
- `components/` — содержала все компоненты приложения вперемешку: от простых кнопок до сложных бизнес-блоков и таблиц.
- `pages/` — страницы маршрутизации.
- `api/` — все запросы к серверу, собранные в единые классы или файлы.
- `hooks/` — кастомные хуки, независимо от того, к какой логике они относились.
- `types/` — все интерфейсы предметной области в глобальной зоне.

### Проблемы старой архитектуры:
1. **Высокая связность (Coupling) и размазанность логики:** Код одной функциональности (например, «Дашборд») был разнесен по множеству директорий (`components`, `hooks`, `api`, `types`). При изменении одной фичи приходилось прыгать по 5-6 разным папкам.
2. **Сложность онбординга и навигации:** По мере роста проекта становилось всё труднее понимать, какие компоненты специфичны для конкретной страницы, а какие — глобальные.
3. **Загрязнение глобального контекста:** Специфичные типы и утилиты находились на одном уровне с базовыми (shared) инструментами, создавая хаос.
4. **Непредсказуемое влияние изменений:** Отсутствие строгих архитектурных границ приводило к тому, что правка в "общем" компоненте могла случайно сломать совершенно другую часть приложения.

## 2. Почему стоит использовать Feature-Sliced Design (FSD)?

Feature-Sliced Design — это архитектурная методология для фронтенд-приложений, которая организует код не по технологиям (компоненты/хуки), а по бизнес-доменам и уровням абстракции.

### Ключевые причины перехода на FSD:
- **Высокая связность внутри (Cohesion) и слабая связность снаружи (Coupling):** Весь код, относящийся к "Дашборду", локализован в папке `features/dashboard`. Это делает модуль независимым, легко тестируемым и модифицируемым.
- **Масштабируемость:** Новые функциональные блоки добавляются как новые слайсы (slices) в папку `features`, не пересекаясь с существующим кодом.
- **Контроль зависимостей (Unidirectional Dependency Rule):** FSD строго регламентирует импорты — модули из нижележащих слоев (например, `shared`) не могут импортировать модули из вышележащих (например, `features`). Это гарантирует отсутствие циклических зависимостей.
- **Структура как документация:** При взгляде на структуру папок сразу понятно, что делает приложение (бизнес-домены), а не просто из чего оно состоит технически.
- **Public API (Изоляция):** Использование `index.ts` (barrel files) позволяет скрыть внутреннюю реализацию (инкапсуляция) и выставлять наружу только необходимые компоненты и хуки.

## 3. Новая структура папок (FSD)

На данный момент проект находится в стадии адаптации под FSD. Главная бизнес-логика (`dashboard`) уже инкапсулирована по принципам Feature-Sliced Design.

### Концептуальные слои (Layers):
1. **`app`** — Инициализация приложения, глобальные стили, корневые провайдеры (`App.tsx`, `main.tsx`).
2. **`pages`** — Композиционный слой. Страницы собирают виджеты и фичи в конечные экраны (например, `Dashboard.tsx`).
3. **`widgets`** — Крупные, самостоятельные UI-блоки страницы, объединяющие несколько фичей (например, `SummaryStats`, `LeadersSuccessors`). Расположены ближе к контексту использования.
4. **`features`** — Бизнес-фичи. Кусочки функциональности, несущие реальную ценность (фильтрация, отображение графиков).
5. **`entities`** — Бизнес-сущности (User, Leader). *На данный момент находятся в процессе выделения из общего кода.*
6. **`shared`** — Общий, переиспользуемый код, не привязанный к конкретному бизнес-контексту (UI-кит, API-клиенты, базовые утилиты).

### Текущая структура директорий:

```text
src/
├── App.tsx                       # [App] Корневой компонент
├── main.tsx                      # [App] Точка входа
├── index.css                     # [App] Глобальные стили
│
├── api/                          # [Shared/API] Базовый API-клиент и адаптеры
│   ├── apiClient.ts
│   ├── auth.ts
│   └── adapters/
│
├── assets/                       # [Shared/Assets] Изображения, иконки
│
├── components/                   # [Shared/UI] Общие переиспользуемые UI-компоненты
│   ├── ErrorBoundary.tsx
│   ├── Layout.tsx
│   └── ProtectedRoute.tsx
│
├── context/                      # [Shared/Lib] Глобальные контексты
│   ├── AuthProvider.tsx
│   └── ColorModeContext.tsx
│
├── features/                     # [Features] Слой бизнес-фичей
│   └── dashboard/                # Слайс предметной области: Дашборд
│       ├── components/           # Внутренние UI-компоненты дашборда (NineBoxMatrix, KpiCard)
│       ├── config/               # Конфигурационные файлы (nineBoxMeta.ts)
│       ├── context/              # Локальный State Management (фильтры)
│       ├── hooks/                # Бизнес-хуки (useLeadersQuery, useStatsQuery)
│       ├── utils/                # Утилиты предметной области
│       └── widgets/              # [Widgets] Самостоятельные блоки страницы
│           ├── SummaryStats.tsx
│           ├── LeadersSuccessors.tsx
│           └── leaders-successors/ # Декомпозиция сложного виджета
│
├── locales/                      # [Shared/Locales] Файлы локализации
│
├── pages/                        # [Pages] Слой страниц
│   ├── Dashboard.tsx             # Собирает компоненты из features/dashboard
│   └── Login.tsx
│
└── types/                        # [Shared/Types] Глобальные типы предметной области
    ├── dashboard.ts
    └── errors.ts
```

### 3.1. Прагматичный подход (Дальнейшие шаги)
В рамках плавного перехода некоторые слои (`shared`, `entities`) пока представлены корневыми папками (`api`, `components`, `types`). В будущем планируется окончательная миграция глобальных переиспользуемых модулей в директорию `src/shared/`, а бизнес-данных в `src/entities/`, чтобы полностью соответствовать строгим канонам архитектуры FSD. Текущая структура решает самую главную проблему: **полную изоляцию логики сложного дашборда.**
